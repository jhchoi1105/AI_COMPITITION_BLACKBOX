## Stage 3에서 바꾼 것

1. CPU Farneback 광류를 KITTI로 파인튜닝된 RAFT-Large로 교체했다. RGB 입력, 폭 384, 세로 8의 배수, 8회 업데이트, 4쌍 배치로 GPU에서 추론한다.
2. 영상 앞뒤에 0을 채우던 시간 평활화를 가장자리 값 연장으로 바꿨다. 일정한 움직임 신호에 인위적인 가속·감속이 생기는 것을 줄인다.
3. 평활 반경을 영상 길이에 맞춰 제한했다. 기존 `_smooth`의 `np.convolve(..., mode="same")`는 입력보다 커널이 길 때 더 긴 배열을 반환한다. 새 경로는 0·1·2프레임 등 짧은 입력에서도 출력 길이를 보존한다.
4. 수평 광류에 5프레임 평활화를 적용해 순간적인 조향 흔들림을 줄였다.
5. 완전히 동일한 프레임 쌍은 광류를 0으로 처리한다. 신경망이 정지 이미지에도 작은 이동을 출력하는 현상을 막는다.

가감속 0.55, 정지 분위수 0.42, 조향 1.1 등 기존 판정 설정은 유지했다. 특히 **영상 내 움직임 하위 분위수를 STOPPED로 보는 한계가 여전히 있다.** 지속적으로 움직이는 영상에서도 정지를 과다 예측할 수 있으며, 이번 변경이 실제 속도·가속도의 완전한 추정을 의미하지 않는다. 잡음이 있는 정지 영상도 완전히 해결된 것은 아니다.

GPU가 없거나 모델 로딩·추론에 오류가 발생하면 Farneback과 새 시간 평활화로 대체한다. 오류 시 파일명과 원인을 출력하므로 서버 로그에서 `fallback`을 확인할 수 있다. CPU 대체 경로는 GPU 경로와 점수가 같다고 보장하지 않는다.

과거 파일 수·처리 순서에 따라 이후 예측을 상수로 바꾸던 전역 시간 예산 분기는 새 제출에서 끈다. 모델 가중치만 캐시하며, 다른 입력 파일의 통계로 예측을 보정하지 않는다. 이에 따라 **평가 전체가 60분 안에 끝나는지는 실제 서버 로그로 확인해야 한다.**

## Stage 3 로컬 비교 — 공식 대회 점수 아님

기존에 로컬에 확보되어 있던 comma2k19 10개 세그먼트를 사용했다. 세그먼트마다 전체 약 60초, 20 Hz 영상에서 실제 간격 2프레임으로 10 Hz를 구성했다. 총 6,000개 시점이다. 20 Hz의 인접 프레임 광류를 계산하고 인덱스만 띄우던 과거 계측과는 조건이 다르다.

ECEF 속도에서 속력·가속도를 구하고, 속도 벡터를 지역 East/North 좌표로 변환해 조향 방향을 만들었다. 과거 `pose_label.py`의 카메라 좌표 회전축과 ECEF 방향 벡터를 직접 내적하는 방법은 사용하지 않았다. 기준값은 정지 0.5 m/s, 가감속 ±0.3 m/s², 조향 ±0.015 rad/s이다. **주최 측의 비공개 라벨 생성 기준을 알아낸 것이 아니라 물리량을 사용한 대리 라벨이다.**

| 전체 10개 세그먼트 | 가감속 Macro-F1 | 조향 Macro-F1 | 두 값 평균 |
|---|---:|---:|---:|
| YY 기존 코드 | 0.2266 | 0.5488 | 0.3877 |
| Farneback + 시간 처리 수정 | 0.2311 | 0.5793 | 0.4052 |
| **RAFT + 시간 처리 수정 — 제출안** | **0.2974** | **0.6231** | **0.4603** |
| RAFT + 도로 평면 속도 추정 실험 | 0.2895 | 0.6231 | 0.4563 |

개발용 앞 6개에서 기존 0.4081 → 제출안 0.4728, 보류용 뒤 4개에서 0.3439 → 0.4183이었다. 도로 평면 추정은 개발 구간에서 열세여서 제출 설정에서는 끄고, 계산도 생략한다.

표본들은 동일 차량·유사 경로이며 일부가 시간상 인접해 있어, 다른 도로·카메라에 대한 독립적인 일반화 검증은 아니다. 고속도로 주행 비중도 높아 STOPPED 평가가 약하다. 전체 지표는 모든 시점을 합쳐 계산한 값이므로 영상별 점수 평균과 다르다. 이 수치를 기존 공식 Stage 3 점수 0.4530과 직접 비교하거나, 공식 점수가 같은 폭으로 오를 것으로 해석하면 안 된다.

짧은 24초 탐색 구간에서 얻은 더 큰 개선값 대신, 위 전체 60초 결과를 최종 근거로 남긴다. 원자료·예측·집계는 `experiments/stage23/proxy_details.json`과 `proxy_summary.json`에서 확인할 수 있다. 데이터·캐시·대리 라벨은 제출 ZIP에 포함하지 않는다.

## Stage 2 실험의 의미와 한계

Faster R-CNN ResNet50 FPN V2로 자동차·오토바이·버스·트럭을 검출하고, 프레임 사이 바운딩 박스 겹침으로 추적한다. 사고 시점 근처의 큰 차량 후보를 고른 뒤, 작은 차량이 처음 검출되기 전의 경로를 국소 광류로 최대 16프레임 거슬러 확인한다.

중앙 주행 통로와 차량 박스가 겹치는 시점을 진입 후보로 쓴다. 실제 차선 경계를 분할한 모델은 아니다. 차가 이미 통로 안에서 처음 검출된 경우에는 박스의 확대와 통로 겹침으로 접근 시작을 추정하는 **실험적 대체 규칙**을 사용한다. 이 값은 정확한 차선 진입 시각과 다를 수 있다. 근거가 부족하면 기존 예측을 유지한다.

공개 영상에 대한 변경은 다음과 같다. 충돌 프레임·회피 공간·진입 방향은 이 5개에서 같았다.

|---|---:|---:|
| S2_001 | 10 | 29 |
| S2_002 | 12 | 12 |
| S2_003 | 9 | 9 |

`t_entry=-1`은 미표기이므로 이 변경이 맞았다는 정확도는 계산하지 않았다. 이 실험은 기존의 일률적인 ‘충돌 24프레임 전’을 실제 영상 속 객체 경로로 대체하려는 후보다. Stage 2 전체 네 항목을 해결한 모델은 아니다. 가벼운 SSDLite도 시험했지만 공개 사고영상에서 차량 누락이 많아 제출에는 포함하지 않았다.

## 검증 및 재현

최종 ZIP을 임시 폴더에 풀어, 네트워크 연결을 차단한 상태에서 검증한다. 검증 스크립트는 원본 제출을 바꾸지 않는다.

```powershell
python experiments/stage23/build.py
python experiments/stage23/package.py
python experiments/stage23/verify_release.py
```

현재 PC의 GPU Python과 `C:/bbv`의 영상 패키지를 함께 사용하도록 검증 스크립트를 구성했다. 외부 데이터 비교를 다시 실행하려면 `C:/bbw/c2k19`의 기존 세그먼트가 필요하다. 제출 코드 자체에는 이 PC의 경로나 검증 데이터 경로가 없다.

검증 결과는 `experiments/stage23/release_verification.json`, ZIP 및 동봉 파일 SHA-256은 `experiments/stage23/manifest.json`에 기록한다. PyTorch 2.8.0 / torchvision 0.23.0 CPU 환경에서 두 모델의 가중치 로딩도 확인했다. GPU 검증은 RTX 4060, PyTorch 2.5.1 / torchvision 0.20.1 환경이며 평가 서버 L40S에서의 전체 실행시간 검증을 대체하지 않는다.

최종 검사 결과: **통과**. Stage 1 공개 10건이 YY와 동일했고, Stage 2 공개 5건의 프레임 번호·범주가 유효했다. Stage 3 공개 영상 5개의 **실제 디코딩 5,992프레임에 정확히 5,992행**을 출력했다. 빈 입력, 1·2·5·50프레임 무손실 정지 영상, CPU 대체 경로, 파일 처리 순서의 영향도 검사했다. Stage 2 추론 13.3초, Stage 3 추론·프레임 수 대조 209.1초, 기준 모델 비교를 포함한 검증 구간 전체 311.3초였다. 서버 평가셋은 더 크므로 이 시간만으로 60분 이내 완료를 확정할 수 없다.
