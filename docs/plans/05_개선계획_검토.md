# 외부 개선계획 검토 (Blackbox_AI_Improvement_Plan.md)

우리가 실제로 측정한 결과와 대조한 것이다. 판정은 **확인됨 / 기각됨 / 미검증** 셋이다.
기각은 "아이디어가 나쁘다"가 아니라 **이 대회의 평가 데이터에서 실제로 시도했고 점수가 내려갔다**는 뜻이다.

## 1. 문제 진단 — 대체로 정확하다

| 항목 | 판정 | 근거 |
|---|---|---|
| Stage 1: 해상도 축소가 고주파 아티팩트를 파괴한다 | **확인됨** | 같은 특징이 256폭 축소에서 신호/잡음 0.07(방향일치 2/5, 무작위), 원본 해상도에서 1.47(5/5). 이미 F부터 수정되어 현재 제출에 반영돼 있다 |
| Stage 1: 사전학습 가중치 부재 | **확인됨** | 다만 현재 제출은 학습 모델을 아예 쓰지 않는 규칙 기반이다 |
| Stage 2: 단순 `argmax`는 노이즈에 취약 | **미검증** | 그럴듯하나 Stage 2 격차가 0.103(전체의 11.8%)이라 우선순위가 낮다 |
| Stage 3: ego-motion이 하늘·주변 차량에 오염된다 | **확인됨** | 전체 프레임 중앙값을 쓰는 현 방식의 실제 결함이다 |
| Stage 3: 시간적 연속성 미반영 | **확인됨** | 예측 라벨 연속구간 중앙값이 **2프레임**이었다. 가감속이 0.1~0.2초마다 뒤집히는 것은 물리적으로 불가능하다 |

## 2. Stage 3 처방 — 전부 이미 시도했고 기각됐다

계획서의 Stage 3 항목은 우리가 I 제출에서 실제로 구현해 낸 것과 사실상 동일하다. **결과는 0.2683 → 0.2347로 하락이었다.**

| 계획서 처방 | 판정 | 측정 결과 |
|---|---|---|
| `raft_large` KITTI 가중치로 밀집 광류 교체 | **기각됨** | 동일 stride·동일 규칙 대조에서 Farneback 0.363 대 RAFT **0.365**. n=50에서 구별 불가. torch 의존성 + 21MB + GPU 시간 + CUDA 미가용 대체경로를 +0.002에 치를 이유가 없다 |
| 소실점 부근 광류를 **조향(Yaw)** 지표로 | **기각됨** | 공개 지표는 steer 0.265 → 0.370으로 올랐으나 **리더보드 Stage 3는 0.2683 → 0.2347로 하락**. 화면비 가설: 공개 영상 1164×874(1.33) 대 평가 추정 1280×720(1.78). 16:9면 세로 30~50% 띠는 지평선이 아니라 **하늘**이다 |
| 하단 노면 **발산**을 가감속 지표로 | **기각됨** | `road_v`(노면 수직흐름) 0.321, `road_mag` 0.388 대 전체 프레임 크기 중앙값 0.393~0.419. 둘 다 더 나빴다 |
| 최빈값 필터 Size=15 | **기각 대기** | I에 포함되어 하락에 기여했을 수 있다. J가 ROI와 이 항목을 분리한다 |
| 화면 상단 하늘 배제 | **기각됨** | 위 `road_*` 실험이 사실상 이 처방이며 더 나빴다 |

**교훈: Stage 3에서 공개 50점 대리지표는 두 번 연속 리더보드와 반대 방향을 가리켰다. 앞으로 Stage 3 변경은 리더보드로만 판정한다.**

## 3. Stage 1 처방 — 동의한다

| 항목 | 판정 |
|---|---|
| 원본 해상도 패치 기반 | **확인됨** — 이미 반영 |
| `legacy_xception` / `efficientnet_b4` / `convnext_tiny` | **미검증, 동의** — timm에 가중치 존재 확인함 |
| **SRM 필터 뱅크 / Bayar 구속 레이어 front-end** | **미검증, 가장 유망** — 계획서에서 나온 항목 중 우리가 아직 안 해본 것 중 가장 값어치 있다 |

단, 지금은 한계가 수치로 나와 있다. F(0.2682)와 I(0.6203)가 정확한 여집합이라 혼동구조를 역산했더니 **판별력(a+b−1)이 +0.31, 임계값만 옮겨 도달할 상한은 약 0.682**다. 1위 0.92814까지의 나머지 0.31은 특징을 바꿔야 얻는다. SRM/Bayar는 정확히 그 자리를 노리는 처방이다.

## 4. Stage 2 처방 — 동의하나 우선순위가 낮다

`fasterrcnn_resnet50_fpn_v2` + ByteTrack, `Depth Anything V2 Small`(Apache-2.0)로 회피 공간을 판정하는 것은 원리적으로 옳다. 다만 Stage 2 격차는 0.103(11.8%)이고, **설정값 하나(`entry_gap`)만 밀어도 계속 오르고 있다**(0.2019 → 0.2555). 모델을 얹기 전에 이 스윕부터 끝낸다.

## 5. 서버 최적화 — 한 항목이 특히 중요하고, 한 항목은 위험하다

| 항목 | 판정 |
|---|---|
| **Stage별 실행시간 측정·자체 타임아웃** | **확인됨. 가장 값어치 있는 지적이다.** 우리는 60분 예산을 **한 번도 측정하지 않았다.** 초과하면 제출 오류로 슬롯이 차감된다 |
| fp16 autocast, `pin_memory`, 배치 극대화 | **미검증** — 현재 제출은 torch를 전혀 쓰지 않아 아직 해당 없음 |
| `CAP_PROP_POS_FRAMES`로 탐색 최적화 | **주의** — 많은 코덱에서 키프레임으로 스냅되어 **부정확**하고 순차 디코딩보다 느릴 수 있다. Stage 3는 모든 프레임이 필요하므로 탐색이 아예 무의미하다 |
| `model/stageX/` 가중치 동봉, `weights=None` + `local_files_only` | **확인됨** — 학습 모델 도입 시 필수 |
| 라이선스 장부 | **확인됨** — `04_사용가능_모델_목록.md`에 정리. 함정 확인: Ultralytics AGPL-3.0, Depth Anything V2 **Large는 CC-BY-NC**(Small만 Apache-2.0), VideoMAE CC-BY-NC, DINOv3 게이트 |
| `torch.manual_seed` 고정 | **부분 확인** — 우리가 겪은 비결정성은 RNG가 아니라 최빈값 필터의 동점 처리였다. 이미 수정했다 |

## 6. 로드맵 — 순서를 바꿔야 한다

| 계획서 | 판정 | 대안 |
|---|---|---|
| 1순위: Stage 3 RAFT 도입 | **기각** | 측정 결과 +0.002. 격차가 최대(53%)인 것은 맞지만 처방이 틀렸다 |
| 2순위: Stage 1 패치 백본 | **승격** | SRM/Bayar front-end + 자체 생성 데이터. 임계값 천장 0.682를 넘는 유일한 길 |
| 3순위: Stage 2 Depth·Tracking | **유지(최하위)** | 먼저 `entry_gap` 스윕을 끝낸다 |

### 개정 로드맵

1. **실행시간 예산 계측·방어** — 초과는 슬롯 차감이다. 모델을 얹기 전에 먼저 한다
2. **Stage 3 진단 종결** (J) — ROI가 범인인지 E의 수정이 범인인지 가른다. 그 다음 Stage 3 학습 파이프라인. 격차의 53%가 여기 있다
3. **Stage 1 SRM/Bayar + 자체 생성 데이터** — 격차의 35%, 천장 0.682를 넘는 유일한 수단
4. **Stage 2 `entry_gap` 스윕 완주** 후 필요시 Depth 도입

## 7. 종합

이 계획서의 **진단은 정확하고 우리 측정과 일치**한다. 새로 얻은 것은 **SRM/Bayar front-end**와 **실행시간 자체 계측** 두 가지이며, 둘 다 채택한다.

반대로 **Stage 3 처방 전체는 우리가 이미 구현해서 리더보드에서 하락을 확인한 것**이다. 계획서가 근거로 삼은 것은 공개 데이터 기준의 그럴듯함인데, 이 대회의 공개 Stage 3 데이터(영상 5개, 라벨 50점, 20fps, 화면비 1.33)는 평가 데이터를 대표하지 못한다는 것이 두 번의 실측으로 확인됐다.
